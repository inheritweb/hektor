# Hektor repository guidance

## Project

Hektor is a local-first TypeScript monorepo. It currently contains a Next.js web
application, shared TypeScript and ESLint packages, and a local Supabase backend.
Treat `README.md` as the detailed development and operations reference.

## Repository map

- `apps/web`: Next.js App Router application, browser tests, and Supabase clients.
- `packages/types`: shared application types and generated Supabase database types.
- `packages/eslint-config`: shared flat ESLint configuration.
- `packages/typescript-config`: shared strict TypeScript configuration.
- `supabase/migrations`: source of truth for database schema changes.
- `.github/workflows`: CI and Vercel deployment workflows.
- `.devcontainer`: reproducible development container and startup scripts.
- `docs`: focused operational documentation.

## Toolchain and commands

Use Node.js 24 and the repository-pinned Yarn 4 release through Corepack. Run
commands from the repository root unless documentation explicitly says otherwise.

- Install dependencies: `yarn install --immutable`
- Start development: `yarn dev`
- Run fast validation: `yarn check`
- Run unit tests: `yarn test`
- Build all workspaces: `yarn build`
- Run the full CI-equivalent suite: `yarn ci`
- Run browser tests: `yarn test:e2e`
- Format files: `yarn format`
- Start local Supabase: `yarn supabase:start`
- Rebuild the local database: `yarn supabase:reset`
- Regenerate database types: `yarn supabase:types`

## Working conventions

- Inspect the existing implementation and nearby tests before changing code.
- Keep changes scoped to the request and preserve unrelated working-tree changes.
- Add or update regression tests when behavior changes or a bug is fixed.
- Prefer workspace scripts over invoking unpinned global tools.
- Commit `yarn.lock` whenever dependency manifests change.
- Do not edit generated files manually. In particular, regenerate
  `packages/types/src/database.ts` with `yarn supabase:types` after schema changes.
- Database structure belongs in versioned migrations, not untracked Supabase
  Studio changes.
- Preserve the browser/server split in `apps/web/lib/supabase`: browser code uses
  `client.ts`; server code uses `server.ts`; session refresh belongs in `proxy.ts`.
- Keep raw environment values only in the ignored root `.env`. Committed app
  `.env` files may contain mappings but not secrets. Never expose privileged
  values through `NEXT_PUBLIC_` variables.
- Do not deploy, modify hosted Supabase resources, or perform destructive remote
  operations unless the user explicitly requests it.

## Verification

Run the narrowest relevant tests during development. Before handing off a normal
code change, run `yarn check` and the relevant unit tests. Run `yarn build` when
the change affects production compilation, configuration, dependencies, or
cross-workspace behavior. Run `yarn test:e2e` for user-visible browser flows when
the required local services are available.

Report which checks ran and any checks that could not run. Do not claim a check
passed without executing it.

## Git and generated changes

- Never discard or overwrite changes you did not create.
- Review `git status` and the relevant diff before editing an already-modified file.
- Do not commit, amend, rebase, force-push, or push unless the user requests it.
- `apps/web/next-env.d.ts` is generated by Next.js; do not treat formatting-only
  churn in that file as an intentional source change.

## Linear

The project Codex configuration declares the Linear MCP server. Use Linear for
issue and project context only after its OAuth connection is authorized. Read
before writing, confirm issue or project identifiers, and summarize any external
changes made.
